# Plan 01: Database migration and RLS

Status: ready for implementation

Depends on: Foundation, complete

Review gate: required before Plan 02 starts

## Objective

Create one repeatable initial Supabase migration containing the complete agreed data model, integrity rules, Row Level Security, public directory view, and generated TypeScript types. This plan does not include application pages or CRUD interfaces.

## Scope

Included:

- All agreed root, member, membership, session, service, care, and leader tables
- Slugs, audit timestamps, archive state, constraints, indexes, and integrity triggers
- Leader-only access to base tables
- Anonymous access to a deliberately reduced public view
- First-leader bootstrap instructions
- Generated Supabase database types

Excluded:

- Auth UI and session cookies
- Application query modules
- Administration pages and forms
- Production database deployment without explicit user instruction
- Seed member data

## Final modeling decisions

These decisions are complete and must not be delegated back to the coding agent:

1. Member removal uses nullable `archived_at timestamptz`. The UI will not hard-delete members.
2. `church`, `ministry`, and `ministry_term` have stable lowercase slugs.
3. A ministry membership can belong to zero or one term group. Enforce uniqueness on `term_group_membership.ministry_membership_id`.
4. A ministry membership can have multiple department assignments, with at most one assignment per department.
5. `ministry_assignment.term_department_id` is required.
6. A session can target the whole term, one group, or one department. At most one of `term_group_id` and `term_department_id` may be present.
7. `session_participant` is the canonical session/member pair. `attendance_record` references only `session_participant` and does not duplicate session or member IDs.
8. Any church member may become a session participant, including someone without a ministry membership. This supports visitors or ad hoc participation while maintaining one participant row per session/member pair.
9. Status fields remain text with check constraints. Attendance values are `present`, `absent`, and `excused`.
10. Historical entities use restrictive foreign keys. Join records may cascade only when deletion of their direct parent is already permitted.
11. The current `leaders` table is a global allow-list for the single-church administration UI. Multi-church leader scoping is deferred until multiple churches are exposed.
12. The public API name remains `member_profile_public`.

## Canonical table expectations

Every entity table uses UUID primary keys generated by `gen_random_uuid()`. Mutable entity tables receive `created_at` and `updated_at`; append-only relationship records receive `created_at` where operational history is useful.

Root:

- `church`: `id`, `name`, `slug`, timestamps
- `ministry`: `id`, `church_id`, `name`, `slug`, timestamps
- `ministry_term`: `id`, `ministry_id`, `name`, `slug`, `start_date`, `end_date`, timestamps
- `term_group`: `id`, `ministry_term_id`, `name`, timestamps
- `term_department`: `id`, `ministry_term_id`, `name`, timestamps

Member:

- `member_profile`: supplied fields plus `archived_at`, timestamps; `user_id` stays nullable and becomes unique when present
- `member_segment`: supplied fields plus timestamps
- `member_segment_membership`: supplied fields plus `created_at`

Membership and assignment:

- `ministry_membership`: supplied fields plus `created_at`
- `term_group_membership`: supplied fields plus `created_at`; one group per ministry membership
- `ministry_assignment`: supplied fields plus `created_at`; department is required

Sessions:

- `session_recurrence_rule`: supplied relationship fields, required non-empty `rule`, timestamps
- `ministry_session`: supplied relationship fields, required `session_date` and non-empty `title`, timestamps
- `session_participant`: supplied relationship fields plus `created_at`
- `attendance_record`: `id`, required unique `session_participant_id`, required constrained `status`, `recorded_at`, `updated_at`
- `session_assignment`: supplied fields plus `created_at`

Service:

- `department_service_role`: supplied fields plus timestamps
- `service_roster`: supplied fields with required non-empty `name`, timestamps
- `service_assignment`: supplied fields plus `created_at`

Care:

- `care_flag`: supplied fields with required non-empty `flag_type`, timestamps
- `care_note`: supplied fields with required non-empty `note`, `created_at`, `updated_at`

Authorization:

- `leaders`: `user_id`, nullable copied `email`, `created_at`; auth-user deletion removes the allow-list row

The coding agent may choose the exact reusable trigger/function names, but must preserve this behavior and English database naming.

## Integrity requirements

Implement all uniqueness and date requirements in `docs/DATABASE.md`, plus these cross-parent invariants:

- A ministry and its terms remain within the same church hierarchy.
- A group membership combines a group and ministry membership from the same term.
- A department assignment combines a department and ministry membership from the same term.
- A recurrence rule or session group/department belongs to the row's ministry term.
- A session assignment combines a session and ministry membership from the same term.
- A service role and roster belong to the same term department.
- A service assignment's department, role, roster, session, and ministry membership resolve to the same ministry term.
- A care flag's member belongs to the same church as the ministry term.
- A session participant's member belongs to the same church as the session's ministry term.

Use declarative constraints when practical. Use small database triggers for invariants that cannot be expressed without unsafe duplication. Trigger exceptions must identify the violated invariant without exposing private row data.

Normalize name inputs at the application boundary later. Database uniqueness for names should be case-insensitive within the documented parent scope where duplicate labels would be confusing.

## Slug rules

- Store lowercase ASCII slugs containing letters, numbers, and single hyphens.
- Enforce a database format check.
- `church.slug` is globally unique.
- `ministry.slug` is unique within `church_id`.
- `ministry_term.slug` is unique within `ministry_id`.
- Slugs are stable identifiers. Renaming a display name does not automatically rewrite an existing slug.

## RLS and grant matrix

All base tables have RLS enabled.

`anon`:

- No base-table access
- `SELECT` on `member_profile_public` only

Authenticated non-leader:

- No domain base-table reads or writes
- May determine only whether their own `user_id` exists in `leaders`
- `SELECT` on `member_profile_public`

Leader:

- `SELECT`, `INSERT`, `UPDATE`, and `DELETE` on domain base tables through policies
- May read leader allow-list data only to the extent required by the current application
- Cannot add, modify, or remove leader authorization through the application in this phase

Create one stable leader-check helper with `SECURITY DEFINER`, an empty fixed `search_path`, fully qualified object names, and execute grants limited to the roles that need it. Revoke unsafe default function privileges. The helper must avoid recursive RLS on `leaders`.

Domain-table policies use the helper in both `USING` and `WITH CHECK`. Do not rely on UI gating or Next.js layouts.

## Public view contract

`member_profile_public` intentionally exposes one row per active member/ministry-term membership and aggregates that membership's department assignments.

Columns:

- `id` as the member ID
- `full_name`
- `birth_year`
- `church_id`, `church_name`, `church_slug`
- `ministry_id`, `ministry_name`, `ministry_slug`
- `ministry_term_id`, `ministry_term_name`, `ministry_term_slug`
- nullable `term_group_id`, nullable `term_group_name`
- sorted `department_ids` UUID array
- sorted `department_names` text array

The view excludes archived members and never exposes phone, user ID, archive timestamps, attendance, care, internal notes, or leader data.

The view is an intentional owner-rights projection so anonymous users can read safe fields while base tables remain leader-only. Configure and document its security options explicitly, restrict grants to `SELECT`, and verify the actual Data API schema and response as `anon`. Do not use `security_invoker = true`, because that would reapply leader-only base-table policies and make the required anonymous directory unreadable.

## Implementation sequence

1. Confirm Supabase CLI availability and local validation path.
2. Create extensions and shared timestamp or authorization helpers.
3. Create tables in dependency order.
4. Add checks, unique constraints, foreign keys, and supporting indexes.
5. Add timestamp and cross-parent integrity triggers.
6. Enable RLS on every base table.
7. Revoke unsafe defaults and create the leader and self-status policies.
8. Create `member_profile_public` and explicit grants.
9. Apply the migration to a clean local or disposable database.
10. Generate `src/types/database.ts` from the migrated schema.
11. Execute the verification matrix and record exact evidence.
12. Stop and request independent review.

## Verification matrix

Migration:

- Clean reset applies the migration once with no manual edits.
- Re-running the reset remains deterministic.
- Generated types compile.

Authorization:

- Anonymous base-table `SELECT`, `INSERT`, `UPDATE`, and `DELETE` fail.
- Authenticated non-leader base-table operations fail.
- Leader domain-table operations succeed.
- A user cannot insert, update, or delete `leaders` through the public API.
- Deleting an auth user removes their leader row and clears an optional member `user_id` as designed.

Public view:

- Anonymous and authenticated reads succeed.
- Only contracted columns exist.
- Phone, user ID, archive metadata, attendance, care, and leader fields cannot be selected.
- Archived members disappear.
- Term, group, and department context is correct and duplicate-free.

Integrity:

- Duplicate memberships, groups, departments, attendance rows, roles, and assignments fail.
- Invalid slug, date range, birth year, empty required text, and attendance status fail.
- Every cross-term and cross-church mismatch listed above fails.
- Restrictive deletes preserve historical records.

Repository:

- `pnpm lint`
- `pnpm typecheck`
- `pnpm format:check`
- `pnpm build`
- No credentials or personal leader email appear in committed files
